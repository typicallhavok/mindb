MinDB Architecture & Interview Study Guide

1. PROJECT OVERVIEW
-------------------
MinDB is a highly specialized, embedded vector database built in Go. It acts as a high-performance gRPC sidecar for microservices.
Key constraints and goals:
- Sub-millisecond latency.
- Exact k-NN (brute-force) rather than approximate (ANN).
- Zero heap allocations on the query path (bypasses Go's Garbage Collector).
- Hard capacity limit: 100,000 vectors.

2. gRPC FLATBUFFERS VS. PROTOCOL BUFFERS
----------------------------------------
Most gRPC services use Protocol Buffers (Protobuf). However, Protobuf requires a deserialization step, which parses the byte stream and allocates new structs on the heap. In Go, this triggers the Garbage Collector (GC), adding unpredictable latency.

Why FlatBuffers?
- Zero-Copy Deserialization: FlatBuffers allows you to access the structured data directly from the raw byte buffer without parsing or allocating new objects.
- GC Avoidance: By avoiding heap allocations, MinDB achieves its goal of 0 allocations on the query path, ensuring strictly deterministic and ultra-low latency.

3. FLAT INDEXING & STRUCT-OF-ARRAYS (SoA)
-----------------------------------------
Most vector DBs (like Milvus, Pinecone) use Approximate Nearest Neighbor (ANN) indexes like HNSW. 
Why Flat Indexing (Brute Force)?
- Scale limit: MinDB caps at 100,000 vectors. At this size, brute-forcing exact k-NN is extremely fast if engineered correctly, avoiding the massive memory overhead and complexity of HNSW.
- Struct-of-Arrays (SoA): Vectors are packed into a single, massive 1D float array (length = 100,000 * dims). This guarantees strict L1/L2 CPU cache sympathy, avoiding cache misses that happen with pointer-chasing in traditional Object-Oriented designs.

4. ASSEMBLY (AVX-512) & COSINE SIMILARITY
-----------------------------------------
Why Assembly?
- MinDB relies on SIMD (Single Instruction, Multiple Data) to achieve its speed.
- It uses custom-written AVX-512 Assembly routines (`.s` files in Go) to process float blocks in 512-bit chunks. This allows the CPU to calculate the dot product of many dimensions simultaneously, vastly outperforming standard Go loops.

Why Cosine Similarity Optimizations?
- Cosine similarity formula: (A · B) / (||A|| ||B||)
- MinDB pre-calculates the magnitude (||A||) of vectors during the `Insert` phase.
- During a `Search`, it only needs to use the AVX-512 routines to compute the dot product, saving massive amounts of CPU cycles on the critical path.

5. CONCURRENCY & ZERO-ALLOCATION (TOMBSTONING)
----------------------------------------------
- Lockless Concurrency: Instead of heavy mutexes on read/write, MinDB uses logical deletes (tombstoning). Deleted vectors just have a boolean flag flipped in a `tombstones` array, which the search loop skips.
- Compaction (RCU): A background goroutine periodically compacts the memory, allocates a new engine state, and atomically swaps the pointer via Read-Copy-Update (RCU). This keeps the search path completely lock-free.
- `sync.Pool`: Used to recycle memory blocks and avoid allocating memory on the fly.

6. DURABILITY (ATOMIC DISK SNAPSHOTS)
-------------------------------------
- Since MinDB is in-memory, it persists data using Disk Snapshots.
- It dumps the raw binary primitive arrays directly to disk, which is nearly instantaneous.
- It uses a Write-Rename atomic pattern (write to `.tmp`, `fsync` to disk, then atomically rename) to prevent state corruption during power loss.
